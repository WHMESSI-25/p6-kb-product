# P6 知识库产品：汕头大学办事指南 RAG 问答

把学校信息公开网「办事指南」栏目的 153 篇指南（其中 148 篇正文为流程图 PDF）做成
可检索、可追问、**带出处引用、不编造**的问答产品。

**线上地址**：<https://whmessi-p6-kb-product.ms.show> （魔搭创空间，免费 CPU 档；
容器冷启动要重新加载模型和索引，约 1 分钟，之后每问 10 秒左右）

## 它能做什么

- 「勤工助学一周最多干几个小时？」→ 每周不超过 8 小时、每月不超过 40 小时（附原文链接）
- 「生源地贷款和校园地贷款有什么区别？」→ 分渠道/材料/流程/银行多维度对比
- 「食堂几点开门？」→ 明确告知知识库没有此信息并给指引，**绝不编造**

## 架构与数据流

```
汕大信息公开网 → crawl.mjs 爬虫 → extract.mjs HTML抽取
                              → extract_pdf.py 下载148个流程图PDF抽取文字层（24.9万字）
        ↓
kb/ingest.py   内容指纹去重(153→112篇) → 清洗 → 500字滑窗切块(415块) → bge-small-zh 向量化
        ↓
kb/store/      chunks.json + vectors.npy（512维）
        ↓
用户提问 → kb/retrieve.py  向量+BM25 双路召回 → RRF 融合排序 Top8
        → 相似度闸门(0.55)：无相关内容 → 拒答+指引（不编造）
        → kb/generate.py  Top8 拼提示词 → DeepSeek 生成 → 解析（资料N）引用 → 答案+出处
```

## 评估与调优（40 题评估集，0/1/2 评分规则，LLM 评分员）

| 轮次 | 改动（每轮只改一处） | 总分 | A 事实 | B 流程 | C 比较 | D 拒答 |
|---|---|---|---|---|---|---|
| 轮0 基线 | — | 86.2% | 85.7 | 95.0 | 62.5 | 100 |
| 轮1 | TOP_K 5→8 | 85.0% | 78.6 | 95.0 | 68.8 | 100 |
| 轮2 | 向量+BM25 RRF 混合检索 | **91.2%** | 89.3 | 95.0 | 81.2 | 100 |
| 轮3 | 提示词三规则（列全/照抄/不混流） | 91.2% | 89.3 | **100** | 75.0 | 100 |

- 轮1 教训：召回变广但上下文稀释，A 类要点覆盖反而下降（净 -1.2pp）
- 轮2 关键发现：纯向量检索够不着「专名藏在低质块」——代理机构名单块排第 247 名，
  BM25 关键词路把它拉回 Top3（+6.2pp，最大单轮涨幅）
- 轮3 教训：「不混流」规则修复 B03 却压制了 C06 的跨文档综合（一涨一跌，净零）

## 本地运行

```bash
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt
# 需环境变量 LLM_API_KEY（DeepSeek Key）
.venv/Scripts/python -m kb.ingest     # 建库（首次约2分钟）
.venv/Scripts/python -m uvicorn app:app --port 8000   # 打开 http://127.0.0.1:8000
.venv/Scripts/python evaluate.py 轮次名               # 40题自动评估
```

## 部署（魔搭创空间）

线上跑的是 <https://whmessi-p6-kb-product.ms.show>：Gradio SDK、2 核 8G 免费 CPU 档，
`LLM_API_KEY` 以密文变量形式配在空间里（不落任何文件）。

- 入口：本地 `app_gradio.py` → 部署仓库里改名 `app.py`（创空间约定入口名）
- 依赖：`requirements-deploy.txt` → 部署仓库里改名 `requirements.txt`
- 向量库：线上用 `kb/store/vectors.npz`。平台 `.gitattributes` 强制 `*.npy` 走 LFS，
  早期版本因此漏交了向量库，克隆下来根本没有向量文件
- 模型：`kb/retrieve.py` 三级加载——仓库内置目录 → 魔搭源（容器同网，秒级）→ HF 镜像；
  HF 的下载超时收到 15 秒，不可达时快速失败而不是干等
- 启动预热：`app_gradio.py` 在启动时就加载模型和 BM25 索引（约 40 秒），
  用户第一问不用替冷启动买单
- 增量更新：`bash scripts/deploy_ms_update.sh "提交说明"`——复用首次部署的本地目录，
  **不要整库重新克隆**（LFS 大文件会卡住）

## 踩坑记录

1. **网页语料是空心 的**：办事指南正文多为图片流程图 PDF，HTML 只能抽到「下载阅读器」
   提示语，153 篇真实文字仅 1194 字。解法：下载 PDF 本体抽文字层，语料 ×208 倍。
2. **同一 PDF 挂多个页面**：24 组内容完全重复（最大一组 5 页共用），按 PDF 内容指纹去重。
3. **拒答防线是双层的**：相似度闸门（0.55）只能拦最离题的问题，D 类拒答题 top1 实测
   高达 0.59-0.63 与正常题区间重叠，最终防线是提示词「资料不足必须明说」。
4. **LLM 评分员有 ±1-2 分噪音**：同一份回答两轮评分可能不同（银行名「广东汕头中行汕大
   支行」为原文原话，一轮判对一轮判错）。单轮涨跌 <2 分不宜过度解读。
5. **线上首问卡了 888 秒，根因有两个**：一是容器里只有 HF 一条模型来源，下载不通时按默认
   超时死等（用户侧看到的就是「转圈十几分钟」）；二是部署仓库从未提交向量库文件
   （被平台强制走 LFS 的 `*.npy` 漏掉了）。教训：**部署要按「代码+数据+依赖」三件一起查**，
   只修看起来最可疑的那一处，会在第二处再摔一次。
